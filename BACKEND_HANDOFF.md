# Volidam QR Menu — техническая передача бэкенд-разработчику

Этот файл объясняет, как устроен текущий фронтенд, что уже сделано, и что нужно
сделать на бэкенде (Express + TypeScript), чтобы сайт стал полноценным
многопользовательским продуктом, а не локальным прототипом.

---

## 1. Что это за проект

QR-меню ресторана **Volidam** (район Алгоритм, Ташкент). Публичная часть —
меню блюд с категориями, поиском и переключением языка (RU/UZ/EN). Плюс
встроенная админ-панель для редактирования меню и управления администраторами.

**Стек фронтенда:** React 18 + TypeScript + Vite + React Router (`HashRouter`).
Без сборки CSS-фреймворков — обычный CSS с переменными (светлая/тёмная тема).

**Важно, и это главная причина, зачем вообще нужен бэкенд:**
Сейчас **вообще нет сервера**. Все данные (меню, админы, тема, язык) хранятся
только в `localStorage` / `sessionStorage` браузера конкретного посетителя.
Это значит:

- Если админ отредактирует меню на своём телефоне — эти изменения увидит
  **только он**, на своём устройстве. Другие посетители сайта их не увидят.
- Нет единого источника правды. Нужен бэкенд с базой данных, чтобы меню было
  одинаковым для всех.

Это и есть основная задача бэкенд-разработчика: перенести то, что сейчас
эмулируется в `localStorage`, в настоящий Express API + БД.

## 3. Как сейчас хранятся данные (то, что нужно заменить на API)

Всё лежит в `localStorage` браузера под этими ключами:

| Ключ                     | Что хранит                                   | Где в коде                  |
|---------------------------|-----------------------------------------------|------------------------------|
| `volidam-menu-items`      | JSON-массив всех блюд меню                    | `src/context/MenuContext.tsx` |
| `volidam-admin-users`     | JSON-массив админов (логин, хэш пароля, роль) | `src/context/AuthContext.tsx` |
| `volidam-admin-session`   | Текущий залогиненный юзер (sessionStorage)    | `src/context/AuthContext.tsx` |
| `volidam-theme`           | `light` / `dark`                              | `src/context/ThemeContext.tsx` |
| `volidam-lang`            | `ru` / `uz` / `en`                            | `src/context/LangContext.tsx` |

**Тему и язык трогать не надо** — это чисто локальные предпочтения браузера,
им бэкенд не нужен (как cookie согласия на куки). А вот **меню и админов
нужно перенести на сервер**.

## 4. Модели данных (TypeScript, файл `src/types/index.ts`)

```ts
export type Lang = 'ru' | 'uz' | 'en';
export type ThemeMode = 'light' | 'dark';
export type AdminRole = 'super' | 'admin';

export interface MenuItem {
  id: string;
  name: string;          // название блюда (как есть, без перевода)
  weight?: string;        // "250 гр", "1 л" и т.п. — свободный текст, необязательно
  price: number;           // цена в сумах, целое число
  tag: string;              // хештег категории, например "salatlar", "kabob"
  photo?: string | null;     // либо URL картинки, либо base64 data:image/... (см. раздел 7)
}

export interface Category {
  tag: string;
  ru: string; uz: string; en: string;   // название категории на 3 языках
}

export interface AdminUser {
  username: string;
  passwordHash: string;   // SHA-256(salt + password), см. раздел 5 — на бэке заменить на bcrypt/argon2
  salt: string;
  role: AdminRole;         // 'super' — может управлять другими админами, 'admin' — только меню
  createdAt: number;
}
```

Категории **не хранятся отдельным списком в базе** — они выводятся автоматически
из `tag` у блюд (см. раздел 6). Это упрощает админке жизнь: если создать блюдо
с новым хештегом — категория появится сама. На бэке эту же логику можно
оставить (просто `SELECT DISTINCT tag`), либо завести отдельную таблицу
`categories`, если появится необходимость её кастомизировать (порядок,
переводы вручную и т.д.) — сейчас для незнакомых тегов название категории
берётся как сам тег с большой буквы, для всех трёх языков одинаково.

## 5. Авторизация и роли (важно для бэкенд-разработчика)

Файл `src/context/AuthContext.tsx`.

### Как это работает сейчас (только на фронтенде, не production-ready):
- Пароль никогда не хранится в открытом виде — на клиенте считается
  `SHA-256(salt + password)` через `crypto.subtle.digest`, и в `localStorage`
  лежит только хэш + соль.
- **Это не настоящая защита** — весь код выполняется в браузере пользователя,
  localStorage читается кем угодно через DevTools. Это временное решение,
  пока нет бэкенда. **На сервере обязательно нужно:**
  - Пароли хэшировать через `bcrypt` или `argon2` (не SHA-256).
  - Логин выдавать настоящую сессию/JWT, а не просто `sessionStorage.setItem`.
  - Все проверки прав (см. ниже) дублировать на сервере — сейчас они
    проверяются только в JS на клиенте, что можно обойти прямым вызовом API.

### Роли:
- `super` — может создавать/удалять админов, назначать/снимать роль `super`
  у других, и редактировать меню.
- `admin` — может только редактировать меню (вкладка "Меню" в админке),
  и менять свой собственный логин/пароль. Вкладку "Админы" не видит толком
  (видит список, но без кнопок управления).

### Защищённый супер-аккаунт:
Есть один "владелец" аккаунт, который нельзя удалить, понизить в роли или
переименовать никому, даже другому `super` админу. Раньше это было
захардкожено по конкретному username во фронтенде — сейчас это не
реализовано ни на фронте, ни на бэкенде, и не должно завязываться на
конкретное имя пользователя. Если такая защита нужна, её стоит выразить
через данные (например, отдельный флаг `is_owner` в таблице `admins`, или
просто "нельзя удалить/понизить последнего супер-админа" — эта последняя
проверка уже есть в реальном бэкенде).

## 6. Категории и группы (структура меню)

Файл `src/data/categories.ts`.

- `DEFAULT_CATEGORIES` — список предустановленных категорий (тег + названия
  на 3 языках): салаты, сомса, кабоблар, напитки и т.д. Всего 14 штук.
- `CATEGORY_GROUPS` — 3 верхнеуровневых раздела, которые видны на стартовом
  экране сайта:
  1. **Milliy taom** (национальные блюда) — салаты, сомса, кабоблар, барбекю,
     уйгурские блюда, рыба и т.д.
  2. **Yevropa taom** (европейские блюда)
  3. **Bar va desertlar** (напитки + мороженое)

  Каждая категория относится к одной из этих трёх групп через список тегов
  `tags: [...]` внутри объекта группы. Если появится категория с тегом,
  которого нет ни в одной группе — она автоматически попадёт в первую
  группу (`milliy`), чтобы никогда не "потеряться" (см. функцию `groupForTag`).

Если бэкенд-разработчик заведёт полноценную таблицу категорий — эту
группировку (`CATEGORY_GROUPS`) тоже стоит перенести в БД, чтобы её можно
было менять без деплоя фронтенда.

## 7. Фото блюд — на что обратить внимание

Сейчас в админке при добавлении блюда фото можно:
- вставить прямую ссылку (URL) на картинку, **или**
- загрузить файл с телефона/компьютера — он на лету сжимается в браузере
  (canvas, до 900px по ширине, JPEG качество 0.75) и превращается в
  **base64 data URL**, который целиком лежит в `localStorage` вместе с блюдом.

Это временное решение и **не подходит для продакшена**:
- `localStorage` ограничен примерно 5–10 МБ на домен — с фотками для 140+
  блюд это быстро закончится.
- base64 в БД — плохая практика, раздувает записи и трафик API.

**Что нужно сделать на бэкенде:** обычная загрузка файлов через `multer` в
Express, сохранение на диск / в S3 / Cloudinary / любое файловое хранилище,
и в поле `photo` у блюда хранить просто URL картинки. Фронтенд к этому уже
готов — он одинаково отображает и base64, и обычный URL (`<img src={photo}>`),
менять на фронте почти ничего не придётся, кроме формы загрузки в
`AdminPanel.tsx` (сейчас она сама конвертирует файл в base64 — нужно будет
заменить на `fetch('/api/upload', { method: 'POST', body: formData })` и
подставлять URL, который вернёт сервер).

## 8. Что конкретно нужно реализовать на Express + TypeScript

Ниже — предлагаемый набор REST-эндпоинтов, которые логически покрывают всё,
что сейчас делает фронтенд через `localStorage`. Названия и структуру можно
адаптировать под свои соглашения, важна суть.

### Меню
- `GET /api/menu-items` — список всех блюд (публичный, без авторизации)
- `POST /api/menu-items` — создать блюдо (нужна авторизация, любой админ)
- `PATCH /api/menu-items/:id` — редактировать блюдо (любой админ)
- `DELETE /api/menu-items/:id` — удалить блюдо (любой админ)
- `POST /api/upload` — загрузка фото (multer), вернуть `{ url }`

### Авторизация
- `POST /api/auth/login` — `{ username, password }` → сессия/JWT + данные юзера
- `POST /api/auth/logout`
- `GET /api/auth/me` — кто сейчас залогинен (для восстановления сессии при
  обновлении страницы — сейчас это эмулирует `sessionStorage`)

### Управление админами (только для роли `super`)
- `GET /api/admins` — список админов
- `POST /api/admins` — создать нового админа `{ username, password }`
  → роль по умолчанию `admin`
- `PATCH /api/admins/:username/role` — назначить/снять `super`
  (запретить снимать последнего `super`)
- `DELETE /api/admins/:username`
  (запретить удалять себя, запретить удалять последнего `super`)
- `PATCH /api/admins/me/username` — сменить свой логин
- `PATCH /api/admins/me/password` — сменить свой пароль (проверять текущий)

Вся эта логика проверок (кто главный, нельзя удалить себя, нельзя удалить
последнего супер-админа) **уже реализована и протестирована на фронтенде**
в `src/context/AuthContext.tsx` — можно использовать её один в один как
референс для бэкенд-логики, там всё довольно явно написано.

## 9. Что менять во фронтенд-коде, когда бэкенд будет готов

Хорошая новость — вся точка интеграции уже вынесена в 2 файла:

1. **`src/context/MenuContext.tsx`** — сейчас читает/пишет `localStorage`
   напрямую. Нужно заменить `loadInitialItems()` на `fetch('/api/menu-items')`,
   а `addItem` / `updateItem` / `deleteItem` — на соответствующие
   `fetch(..., { method: 'POST'/'PATCH'/'DELETE' })`. Компоненты (`MenuPage`,
   `AdminPanel`), которые используют `useMenu()`, менять не придётся —
   у них уже есть готовый интерфейс `{ items, categories, addItem, updateItem,
   deleteItem }`.

2. **`src/context/AuthContext.tsx`** — аналогично, заменить работу с
   `localStorage`/`sessionStorage` на вызовы `/api/auth/*` и `/api/admins/*`.
   Интерфейс наружу (`useAuth()`) можно оставить тем же — `login`, `logout`,
   `createUser`, `deleteUser`, `setUserRole`, `changeOwnPassword`,
   `changeOwnUsername`, `currentUser`, `currentRole`, `isSuperAdmin`, `users`.

Остальной код (страницы, компоненты, стили) вообще не завязан на то, откуда
берутся данные — он просто использует хуки `useMenu()` и `useAuth()`. Это
специально сделано так, чтобы подключение бэкенда не требовало переписывать
интерфейс.

## 10. По мелочи, что ещё стоит знать

- **Роутинг:** используется `HashRouter` (адреса вида `/#/menu`, `/#/admin`).
  Это осознанный выбор, чтобы сайт работал как статика без настройки сервера
  под SPA-роутинг. Если бэкенд разработчик настроит нормальный Express-сервер
  с fallback на `index.html` — можно будет переключить на `BrowserRouter` для
  чистых URL (`/menu`, `/admin`), это одна строчка в `src/App.tsx`.
- **i18n:** переводится только интерфейс (кнопки, заголовки категорий,
  сообщения). Названия самих блюд — как их ввели в админке, без перевода
  (у ресторана меню и так на смеси русского/узбекского, как в оригинале).
- **Сборка:** `npm run build` собирает статику в `dist/` (`tsc -b && vite build`).
  Готовые файлы из `dist/` можно раздавать Express-ом как статику
  (`express.static('dist')`) вместе с API на том же сервере, либо хостить
  отдельно (Vercel/Netlify) и просто указывать `API_URL` на бэкенд.
- **Seed-данные:** если нужно проинициализировать базу начальным набором
  блюд — весь текущий список (~140 позиций) лежит в `src/data/seedItems.ts`
  в готовом виде, можно один в один использовать как seed-скрипт для БД.
